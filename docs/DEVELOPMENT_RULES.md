# AISMM — Engineering Principles & Development Rules

**Document Version:** 1.0.0  
**Status:** Active / Non-Negotiable  
**Audience:** All Core Engineers & AI Systems  

---

## 1. Core Architectural Laws

### Rule 1.1: Platform-Agnostic Core
The core business, scheduling, AI, and analytics logic MUST NEVER contain platform-specific conditionals (e.g. `if platform == 'instagram': ...`). All platform-specific behaviors belong strictly inside the Platform Adapter layer (`backend/app/core/platform_adapters/`).

### Rule 1.2: Capability-Driven Operations
Before attempting any platform operation (e.g. posting a video, fetching comments, deleting a post), code MUST verify that the adapter declares that capability via `adapter.has_capability(PlatformCapability.XYZ)`. If unsupported, the system must raise `UnsupportedCapabilityError` rather than silently failing or attempting invalid requests.

### Rule 1.3: Normalization-First
All platform inputs (posts, comments, metrics, webhooks) MUST be converted into internal normalized data structures (`UniversalContent`, `UniversalMedia`, `CommentData`, `AnalyticsData`, `NormalizedMetric`) immediately upon ingestion. Downstream AI models and services only process normalized types.

## 2. Security & Secrets Management

### Rule 2.1: Zero Secret Exposure
API keys, OAuth client secrets, encryption keys, SMTP passwords, and database credentials MUST NEVER be hardcoded, committed to version control, logged in application logs, or exposed to frontend responses.

### Rule 2.2: ORM-Level Vault Encryption
All sensitive data (OAuth access tokens, OAuth refresh tokens, TOTP secrets, recovery codes) MUST be encrypted at rest in the database using the `EncryptedText` TypeDecorator and `SecretVault` (AES-256 / PBKDF2). In-memory values are decrypted on demand and never logged.

### Rule 2.3: Strict Tenant Isolation
Every database query affecting user resources (posts, social accounts, schedules, comments, metrics, sessions) MUST include an explicit `user_id == current_user.id` filter. Cross-user access or un-scoped queries are strictly forbidden.

### Rule 2.4: Bcrypt Constraints & Password Security
All user passwords must be verified against the maximum length of 72 UTF-8 bytes to prevent bcrypt truncation vulnerabilities. Password hashes must use bcrypt with minimum 12 rounds.

### Rule 2.5: Safe OAuth & State Validation
OAuth initiation must generate 32-byte cryptographic random state parameters, persist them in `OAuthState` with SHA-256 state hashes, store encrypted PKCE code verifiers, enforce a 10-minute expiry window, and immediately mark states as consumed upon callback receipt to prevent replay attacks.

## 3. Truthful Telemetry & Zero-Fake Policy

### Rule 3.1: No Fabricated Production Metrics
The backend and frontend MUST NEVER fabricate synthetic followers, impressions, reach, or engagement metrics when real data is unavailable. If an account has zero data or a provider is unreachable, the system must report zero or an explicit unavailable/offline state.

### Rule 3.2: Explicit Development Isolation for Fallbacks
Any convenience fallbacks (e.g. returning OTP in response body when SMTP is not configured) MUST be strictly gated by `settings.ENVIRONMENT in {"development", "local", "test"}` AND explicit config checks. In production or staging, the system must fail loud with HTTP 502/503 and clear error diagnostics.

### Rule 3.3: No Silent Error Masking
Catch blocks MUST NOT silently swallow exceptions or return fake `status: "success"` objects. Exceptions must be logged with correlation IDs and returned as structured HTTP error payloads.

## 4. API & Schema Standards

### Rule 4.1: Pydantic v2 & Strong Typing
All API request payloads and response bodies MUST use strongly-typed Pydantic schemas in `backend/app/core/schemas/`. Do not use raw dictionary responses.

### Rule 4.2: Dependency-Injected Authentication
Protected API endpoints must declare explicit authentication dependencies:
- `get_current_user`: For basic authenticated user operations.
- `get_current_verified_user`: For all social management, content, scheduling, and AI operations.
- `get_current_active_superuser`: For administrative routes.

### Rule 4.3: Correlation ID & Latency Tracking
Every HTTP response MUST include `X-Correlation-ID` and `X-Process-Time-Ms` headers generated by backend middleware.

---

## 5. Database & Migration Discipline

### Rule 5.1: No Manual Schema Alterations
All database schema changes MUST be implemented via Alembic migrations in `backend/alembic/versions/`. Schema changes without corresponding migrations are rejected.

### Rule 5.2: Cross-Database Compatibility
All SQLAlchemy model column types must support both PostgreSQL 16 and SQLite 3:
- Use `GUID()` TypeDecorator instead of raw Postgres UUID.
- Use `EncryptedText()` for encrypted strings.
- Use standard JSON types compatible with SQLite and Postgres.

### Rule 5.3: Foreign Key Constraints & Cascades
All child relationships (e.g. `SocialAccount`, `Post`, `Schedule`, `PostPublication`) MUST declare explicit `ondelete="CASCADE"` or `ondelete="SET NULL"` foreign key constraints.

## 6. AI Engine & Research Discipline

### Rule 6.1: Research-Validated Baselines
AI engines must adhere to research specifications:
- **Sentiment**: Dual-phase VADER + emoji lexicon weighting.
- **Scheduling**: Random Forest + Gradient Boosting ensemble with holdout evaluation.
- **Growth**: Platform-specific Random Forest Regressors with $R^2$ tracking.
- **Auto-Reply**: TF-IDF (1,2-grams) + Logistic Regression with human-in-the-loop confidence thresholds.
- **Hashtags**: Top-K statistical frequency/density ranking.

### Rule 6.2: Clean Provider Abstraction
AI inference engines must maintain provider independence. Failure of an AI provider or model must return a clean error without crashing the host application.

---

## 7. Testing & Quality Assurance

### Rule 7.1: Evidence-Based Verification
A test is valid only if it asserts actual state transitions, database writes, schema validations, or cryptographic properties. Tests that merely mock everything without asserting contracts do not constitute completion evidence.

### Rule 7.2: Zero-Regression Requirement
All changes must pass the complete backend test suite (`pytest backend/tests`) and frontend verification (`npm test`, `npm run build`, `npm run lint`) before being committed.

### Rule 7.3: Git Commit Cleanliness
Commit messages must follow Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`). Never commit temporary debug files, credentials, or `.env` files.
